# 파인튜닝 vs RAG 비교 실험

**"멍청한 모델을 파인튜닝하면 RAG가 필요 없어지는가?"에 대한 실증 답변**

## 배경

프로젝트 진행 중 "RAG 대신 그냥 작은 모델을 파인튜닝하면 되지 않나?"라는 질문이 나와서, 실제로 검증해봤습니다.

## 방법

1. `Qwen2.5-0.5B-Instruct`를 **LoRA**(경량 파인튜닝, RTX 4070 8GB에서 51초 학습)로 미세조정
2. 학습 데이터: 팀 공식 벤치마크 61문항 중 **실제 QA 53개만 사용** (트릭/가상 질문 8개는 학습에서 완전히 제외 — 모델이 "한 번도 못 본 질문"에 어떻게 반응하는지 보기 위함)
3. 학습된 모델을 두 그룹에 테스트:
   - (A) 학습 데이터에 포함됐던 질문
   - (B) 학습 데이터에 전혀 없던 트릭 질문 (홀드아웃)
4. 같은 트릭 질문을 RAG 파이프라인(`grounding_check` 포함)에도 물어봐서 비교

## 결과

| 질문 유형 | 파인튜닝 모델 | RAG(grounding_check) |
|---|---|---|
| **학습에 포함된 질문**("Pocket의 역할은?") | "Pocket는 휴대용으로 사용하는 기능입니다" — **오답** (정답: "2D 형상 공간을 파내는 기능") | (검색 기반이라 원문 그대로 인용 가능) |
| **학습에 없던 트릭 질문**("퀀텀 머시닝") | "Quantum Machining은... AI 기능입니다" — **환각 지속** | "The provided manual does not contain this information." — **정확히 거절** |

## 해석

### 1. 예상했던 결과: 트릭 질문에서 여전히 환각
파인튜닝은 "한 번도 본 적 없는, 존재하지 않는 개념"에 대해 여전히 그럴듯하게 지어냅니다. 이건 파인튜닝의 근본적 한계입니다 — **학습 데이터에 없는 질문에 "모른다"고 답하도록 만드는 것 자체가 파인튜닝만으로는 어려운 문제**입니다 (별도의 거부 학습 데이터·기법이 필요).

### 2. 예상 밖의 추가 발견: 적은 데이터로는 학습조차 제대로 안 됨
더 흥미로운 건, **학습 데이터에 포함됐던 질문조차 정답을 재현하지 못했다는 점**입니다. 53개 예제·8에폭(51초) 학습으로는 "Pocket"이라는 CATIA 전문 용어를 일반 단어(주머니)와 구분하지 못했습니다. 이는:
- 의미 있는 파인튜닝을 하려면 **훨씬 많은 데이터(수백~수천 건)와 학습 시간**이 필요하다는 뜻
- 반면 RAG는 **데이터 준비나 학습 과정 없이, 매뉴얼 PDF만 있으면 즉시 동작**

## 결론

| 항목 | 파인튜닝 | RAG |
|---|---|---|
| 새 질문(학습 안 한 것) 대응 | 여전히 환각 위험 | grounding_check로 매번 검증 |
| 적은 데이터로 신뢰성 확보 | 어려움(이번 실험에서 확인) | 문서만 있으면 바로 가능 |
| 매뉴얼 업데이트 시 | 재학습 필요 | 재인덱싱만 하면 됨 |
| 출처 인용 | 불가능 | 가능 (P.12 등) |

**"파인튜닝으로 성능을 올리자"는 방향은 이번 프로젝트(환각 방지·출처 인용이 핵심)에는 RAG보다 비효율적임을 실증으로 확인했습니다.** 이 실험 자체가 "왜 RAG를 선택했는가"에 대한 근거 자료입니다.

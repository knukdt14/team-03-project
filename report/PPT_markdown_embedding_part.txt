====================================================
PPT 슬라이드 초안 - 담당 파트: PDF→Markdown 변환 & 임베딩 모델 개선
====================================================

[슬라이드 1] 제목
----------------------------------------------------
PDF→Markdown 변환 & 임베딩 모델 교체를 통한 RAG 검색 품질 개선

부제: 청킹 구조 보존과 다국어 임베딩이 실제로 성능에 미치는 영향 실측


[슬라이드 2] 문제 인식 (기존 파이프라인의 한계)
----------------------------------------------------
- 기존 로더: PDF에서 순수 텍스트만 추출 + "이미지 N개 포함" 태그만 붙임
  -> 제목/표/리스트 같은 문서 구조 정보가 전부 사라짐
  -> 서로 다른 주제가 한 청크에 섞이는 문제 발생
  -> 정보량이 거의 없는 "이미지 태그 전용 청크"가 검색 결과 상위에 노이즈처럼 자꾸 뜸

- 기존 임베딩 모델(all-MiniLM-L6-v2)은 사실상 영어 전용
  -> 한국어 질문이 영어 매뉴얼과 벡터 공간에서 잘 안 붙는 문제 실측 확인
  -> 근소한 차이로 정답 청크가 검색 top-k 밖으로 밀려나는 사례 다수 발견


[슬라이드 3] 시도 1 - PDF -> Markdown 변환 (pymupdf4llm)
----------------------------------------------------
- 기존 PyMuPDF 텍스트 추출 대신, pymupdf4llm으로 제목(#/##/###)·표·리스트 구조를 보존한
  Markdown으로 추출
- MarkdownHeaderTextSplitter로 헤더 경계부터 먼저 나눈 뒤 chunk_size로 재분할
  -> 한 청크 안에 여러 주제가 섞이는 것을 줄임
- 기존 벡터DB(chroma_db_multimodal)와 별도로 chroma_db_markdown을 만들어
  나란히 비교 (기존 파이프라인은 안 건드림)


[슬라이드 4] 시도 2 - 다국어 임베딩으로 교체
----------------------------------------------------
- 기존: sentence-transformers/all-MiniLM-L6-v2 (영어 위주)
- 교체: sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 (다국어)
- 재학습이나 재청킹 없이 임베딩 함수 인자 하나만 바꾸면 적용 가능한 저비용 개선
- 마크다운 로더 + 다국어 임베딩 조합을 별도 벡터DB(chroma_db_markdown_multilingual)로 구성


[슬라이드 5] 결과 - 모델별 성능 비교 (Strict RAG F1)
----------------------------------------------------
                기존(영어전용)    마크다운       마크다운+다국어
Qwen 0.5B         0.6018          0.6105          0.6518   (+0.050)
Qwen 3B           0.8105*         0.8105          0.8228   (+0.012)

* 이 값은 이후 발견된 vect/ git 손상 이전에 측정되어 재검증 필요 (슬라이드 8 참고)

- 마크다운+다국어 조합이 모든 모델에서 가장 높은 점수
- 모델이 작을수록(0.5B) 임베딩 개선 효과가 더 크게 나타남(+0.050)
  -> 검색 품질이 나쁠수록 모델 크기로 커버가 안 되고, 검색 개선이 더 중요해짐

[교차 검증] 팀원의 고난도 38문항 평가셋으로도 재확인
                    Direct F1   RAG F1    격차
Solar (팀원 평가)     0.6163     0.6517    +0.0354
Qwen 0.5B (본 파이프라인) 0.6174   0.6619    +0.0445
-> Direct 점수는 두 모델이 거의 동일 -> RAG 적용 후 저희 조합이 더 높고 격차도 더 큼
-> 마크다운+다국어 임베딩 조합이 실제로 검색 품질을 끌어올렸다는 교차 검증


[슬라이드 6] 안 좋았던 것 / 예상과 달랐던 것
----------------------------------------------------
1. 마크다운 로더 단독 효과는 생각보다 작았음 (+0.003 ~ +0.009)
   - 기대: 구조 보존하면 검색이 확 좋아질 줄 알았음
   - 실제: 청킹 방식보다 임베딩 모델 자체의 언어 커버리지가 훨씬 큰 변수였음

2. 모델이 커질수록(3B) 임베딩 교체 효과가 줄어듦 (+0.012)
   - 강한 모델은 다소 부정확한 검색 결과도 어느 정도 만회해서 답변함
   - 반대로 말하면, 약한 모델/저자원 환경일수록 검색 품질 투자가 더 중요하다는 뜻

3. 특정 질문("솔리드 파트 확장자는?" 등)은 여러 방법을 다 써도 여전히 실패
   - chunk_size를 줄여도, 임베딩을 다국어로 바꿔도 top-k 안에 정답 청크가 안 들어옴
   - 정답 문장은 실제로 매뉴얼에 있는 것을 확인했는데도 검색이 못 찾음
   - 결론: 청킹/임베딩 튜닝만으로는 100% 해결 안 되는 근본적으로 어려운 케이스가 존재


[슬라이드 7] 발견한 이슈(버그) 1 - 검색 결과 노이즈
----------------------------------------------------
- 이미지 태그만 있고 본문이 거의 없는 페이지("이미지 N개 포함"만 있는 청크)가
  정보량이 적어서 임베딩 공간에서 여러 무관한 질문에 대해 최상위로 검색되는 현상 발견
- 한국어 질문, 영어 질문 둘 다에서 동일한 "빈 청크"가 1위로 잡히는 걸 직접 확인
- 마크다운 로더로 전환하면서 실제 본문 구조가 보존돼 이 문제가 자연스럽게 해결됨


[슬라이드 8] 발견한 이슈(버그) 2 - 벡터DB git 추적 손상
----------------------------------------------------
- 증상: 벡터스토어 검색이 top_k(2/4/6) 값과 무관하게 문서를 항상 1개만 반환
- 원인: .gitignore에 vect/ 를 등록했지만, 이미 git이 추적 중이던 파일이라 안 풀림
  -> 팀원이 git merge 할 때마다 로컬에서 새로 만든 인덱스를 커밋된 옛날 파일이 덮어씀
  -> 메타데이터와 실제 인덱스 파일이 어긋나서 검색이 사실상 고장난 상태가 됨
- 팀원(다른 팀원)이 먼저 발견/공유한 버그를 이 컴퓨터에서도 재현 확인
- 조치: 벡터DB 재빌드 + git 추적 완전히 해제
- 교훈: 이전에 측정했던 일부 벤치마크 수치는 이 버그 발견 이전에 측정된 것이라 재검증 필요


[슬라이드 9] 발견한 이슈(버그) 3 - GPU 미사용 / VRAM 부족
----------------------------------------------------
- 임베딩 계산 코드가 GPU가 있는데도 강제로 CPU만 쓰도록 설정되어 있었음 -> GPU 자동 감지로 수정
- 비교 실험 중 한 스크립트 안에서 로컬 LLM을 두 번 연달아 로드했더니
  8GB GPU 메모리가 부족해져 일부 레이어가 CPU로 넘어가며 극도로 느려짐(1시간 넘게 안 끝남)
- 교훈: 모델을 여러 설정으로 비교할 때는 반드시 완전히 분리된 프로세스로 실행해야 함


[슬라이드 10] 발견한 이슈(버그) 4 - API 비용 문제
----------------------------------------------------
- 더 큰 모델(7B)을 API 방식으로 테스트했더니, 벤치마크 도중 무료 크레딧이 소진되어
  결제 오류(402 Payment Required)가 여러 문항에서 발생
- 에러 메시지가 그대로 "답변"으로 채점되면서, 실제로는 무효한 성능 점수(F1)가
  마치 정상 결과처럼 보였음 -> 답변 원문을 직접 확인해서 걸러냄
- 교훈: API 기반 대형 모델 벤치마크는 반드시 답변 원문을 직접 확인할 것.
  숫자만 보면 결제 오류로 인한 무효 데이터를 놓치기 쉬움


[슬라이드 11] 결론 및 시사점
----------------------------------------------------
1. 검색 품질 개선(임베딩 모델 교체)이 로더 변경보다 효과가 컸음
2. 자원이 부족한 환경(작은 모델)일수록 검색 품질 투자 효과가 더 크게 나타남
3. 청킹/임베딩만으로는 못 푸는 근본적으로 어려운 검색 케이스가 존재함 -> 향후 과제
4. 실험 과정에서 인프라 버그(git 추적, GPU 설정, API 비용)를 여러 건 직접 찾아
   해결한 것 자체가 프로젝트의 실질적 성과


[슬라이드 12] 향후 과제
----------------------------------------------------
- 3B + 마크다운 + 영어전용 임베딩 조합 재검증 (vect/ 손상 이전 수치라 신뢰도 낮음)
- 더 큰 임베딩 모델(bge-m3 등)로 추가 비교 (현재 환경 torch 버전 문제로 보류 중)
- 청킹/임베딩으로도 안 풀리는 특정 질문 유형에 대한 별도 대응 방안 검토

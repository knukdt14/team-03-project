# RAG 성능 튜닝 실험 리포트

**CATIA 매뉴얼 RAG 시스템의 성능을 좌우하는 요인을 정량 측정한 전체 기록입니다.**

`Qwen2.5-1.5B` / `Qwen2.5-3B` · 61문항 + 18문항 벤치마크 · BERTScore F1 · RTX 5060 8GB

---

## 최종 결론 요약

### 실측 최고 성능: **F1 = 0.7654**
```yaml
모델:                Qwen/Qwen2.5-3B-Instruct (local GPU)
RAG:                 Strict RAG ON
chunk_size/overlap:  600 / 100
top_k:               4
Query Expansion:     OFF
```
> **현재 `src/config.py`가 이미 이 조합입니다 — 설정 변경 불필요.**

### 레버별 효과 순위

| 순위 | 레버 | 효과 크기 | 판정 |
|:---:|---|---|:---:|
| 1 | **RAG 적용 (On/Off)** | **+0.057 ~ +0.100** | 🟢 결정적 |
| 2 | **모델 크기 (1.5B→3B)** | **+0.048** (RAG On 기준) | 🟢 큼 |
| 3 | Query Expansion | +0.022 ~ **-0.004** (조건부) | 🟡 상황따라 |
| 4 | chunk_size / overlap / top_k | 편차 0.007 (3B 미재현) | 🔴 노이즈 |

**핵심 3줄**
1. **RAG 적용이 압도적** — 3B 기준 F1 +0.100, 특히 할루시네이션 유도 질문에서 **만점(1.0000)** 달성
2. **그다음이 모델 크기** — 1.5B→3B로 +0.048 (파라미터 튜닝의 **20배** 효과)
3. **세부 튜닝은 기대 이하** — Query Expansion은 모델·질문 유형 따라 갈리고, 검색 파라미터는 사실상 무의미

## 1. 실험 환경 및 방법

| 항목 | 값 |
|---|---|
| 비교 모델 | Qwen2.5-1.5B-Instruct, Qwen2.5-3B-Instruct (local, fp16) |
| 평가 지표 | BERTScore F1 (`lang="ko"`) |
| 기본 평가셋 | **61문항** — General QA / Specific QA / Trick·Unanswerable 8문항 (`src/evaluation.py`) |
| 어려운 평가셋 | **18문항** — 정답 기능명을 질문에서 배제하고 우회 서술 (`src/hard_benchmark.py`) |
| 벡터스토어 | Chroma, 7,064 청크 / 32개 PDF |
| 임베딩 | `sentence-transformers/all-MiniLM-L6-v2` |
| GPU | RTX 5060 Laptop 8GB |
| 생성 설정 | `temperature=0.01`, `do_sample=False` (결정론적) |

### 평가셋 확장 이력
- 최초 **5문항** → 파라미터 비교 시 노이즈에 묻히는 문제 발견
- **16문항**으로 1차 확장 → 여전히 그리드서치가 오버피팅
- **61문항**으로 최종 확장 (전부 PDF 원문 기반으로 ground_truth 검증)
- 추가로 **어려운 세트 18문항** 신설 (6번 참고)

### 3가지 응답 모드
| 모드 | 동작 |
|---|---|
| **Direct LLM (RAG Off)** | 검색 없이 모델 사전지식만으로 답변 |
| **Strict RAG (RAG On)** | 매뉴얼 검색 결과만 근거로 답변, 없으면 "매뉴얼에 없음" |
| Adaptive Fallback RAG | 매뉴얼에 없으면 Direct LLM으로 폴백 |

> 본 리포트의 주 비교는 **Direct LLM vs Strict RAG** 입니다.

## 2. RAG On/Off 비교

**프로젝트의 핵심 증거입니다.** 동일 코드 경로(`experiments/test_bigger_model.py`), Query Expansion OFF, 61문항.

### 2-1. Qwen2.5-1.5B

| 질문 유형 | RAG Off F1 | RAG On F1 | 격차 |
|---|:---:|:---:|:---:|
| General QA | 0.6599 | 0.7181 | **+0.0582** |
| Specific QA | 0.6707 | 0.7079 | **+0.0372** |
| Trick/Unanswerable | 0.6097 | 0.7482 | **+0.1385** |
| **전체 평균** | **0.6592** | **0.7165** | **+0.0574** |

### 2-2. Qwen2.5-3B

| 질문 유형 | RAG Off F1 | RAG On F1 | 격차 |
|---|:---:|:---:|:---:|
| General QA | 0.6689 | 0.7394 | **+0.0705** |
| Specific QA | 0.6675 | 0.7232 | **+0.0557** |
| **Trick/Unanswerable** | 0.6415 | **1.0000** | **+0.3585** |
| **전체 평균** | **0.6645** | **0.7648** | **+0.1003** |

### 해석
- **트릭 질문에서 격차가 압도적** — RAG Off는 존재하지 않는 기능을 그럴듯하게 지어내다 감점되고, RAG On은 "매뉴얼에 없다"고 정직하게 답해 정답 처리
- **3B의 트릭 문항 F1 = 1.0000 (만점)** — 8개 트릭 문항 전부에서 **단 한 번도 지어내지 않음**. 할루시네이션 완전 제거
- General/Specific QA에서도 일관되게 +0.04~0.07 개선

📁 `rag_on_off_1.5b_results.csv`, `rag_on_off_3b_results.csv`

## 3. 모델 크기 비교 (1.5B vs 3B)

동일 조건(벡터스토어·평가셋·QE OFF)에서 모델만 교체.

| 지표 | 1.5B | 3B | 변화 |
|---|:---:|:---:|:---:|
| RAG Off F1 | 0.6592 | 0.6645 | +0.0053 |
| **RAG On F1** | 0.7165 | **0.7648** | **+0.0483** |
| **RAG On/Off 격차** | +0.0574 | **+0.1003** | **격차 1.75배 확대** |
| 트릭 문항 RAG On | 0.7482 | **1.0000** | +0.2518 |

### 유형별 상세

| 질문 유형 | 1.5B RAG On | 3B RAG On | 개선폭 |
|---|:---:|:---:|:---:|
| General QA | 0.7181 | 0.7394 | +0.0213 |
| Specific QA | 0.7079 | 0.7232 | +0.0153 |
| Trick/Unanswerable | 0.7482 | **1.0000** | **+0.2518** |

### 핵심 발견 3가지
1. **RAG Off는 거의 안 올랐는데(+0.005) RAG On만 크게 올랐다(+0.048)**
   → 3B가 되어도 **사전지식만으론 여전히 CATIA를 모름**. 대신 **주어진 매뉴얼을 활용하는 능력**이 확실히 좋아짐
2. **격차가 오히려 커짐 (+0.057 → +0.100)**
   → "소형 LLM + RAG" 프로젝트 스토리가 3B에서도 유효하며, 오히려 더 설득력 있음
3. **할루시네이션 완전 제거** (트릭 만점) — 실용 관점에서 가장 중요한 개선

## 4. Query Expansion 비교

동의어·영문 기능명을 LLM으로 확장해 검색 쿼리에 덧붙이는 기법. **결과가 조건에 따라 갈립니다.**

### 4-1. 전체 결과

| 모델 | 평가셋 | QE OFF | QE ON | 격차 |
|---|---|:---:|:---:|:---:|
| 1.5B | 기본 세트 (61문항) | 0.7165 | 0.7265 | +0.0100 |
| 1.5B | **어려운 세트 (18문항)** | 0.6788 | **0.7010** | **+0.0222** |
| **3B** | 기본 세트 (61문항) | **0.7654** | 0.7611 | **-0.0037** |

### 4-2. 1.5B 기본 세트 — 유형별 분해

| 질문 유형 | QE OFF | QE ON | 격차 |
|---|:---:|:---:|:---:|
| General QA | 0.7181 | 0.7280 | +0.0099 |
| **Specific QA** | 0.7079 | 0.7059 | **-0.0020** |
| **Trick/Unanswerable** | 0.7482 | 0.8081 | **+0.0598** |

**문항 단위 승패: 개선 23 / 악화 23 / 변화없음 15 — 사실상 반반**

즉 평균 +0.010은 전반적 개선이 아니라 **트릭 문항이 끌어올린 값**입니다.

> ⚠️ **트릭 문항 상승은 좋은 이유가 아닐 수 있음**
> 존재하지 않는 기능을 묻는 질문에 확장 키워드를 붙이면 검색이 더 엉뚱해지고 → 모델이 "매뉴얼에 없다"고 답할 확률이 올라갑니다. 트릭 문항에선 그게 정답이라 점수가 오른 것이므로, **검색이 좋아져서가 아니라 나빠져서 맞았을** 가능성이 있습니다.

### 4-3. 어려운 세트 — 여기서는 진짜 효과

트릭 문항이 **하나도 없는데도** +0.0222, **개선 14 / 악화 4**로 뚜렷한 우세.

| | 격차 | 질문 |
|---|:---:|---|
| 최다 개선 | **+0.129** | "두 직선이 만나는 뾰족한 부분을 둥근 원호로..." (→ Corners) |
| 개선 2위 | +0.061 | "3차원 덩어리에서 안쪽으로 파내어 빈 공간을..." (→ Pocket) |
| 개선 3위 | +0.061 | "커서가 화면 눈금 교차 지점에 착 달라붙게..." (→ Snap to point) |
| 최다 악화 | **-0.087** | "사출 금형에서 부품이 잘 안 빠질 때..." (→ Draft Angle) |

→ **어휘가 안 겹치는 우회 표현 질문에서는 동의어 확장이 실제로 검색 간극을 메워줌**

### 4-4. 3B에서는 역효과

| 질문 유형 | QE OFF | QE ON | 격차 |
|---|:---:|:---:|:---:|
| General QA | 0.7367 | 0.7349 | -0.0018 |
| Specific QA | 0.7259 | 0.7191 | -0.0068 |
| Trick/Unanswerable | 1.0000 | 1.0000 | 0.0000 |

3B는 이미 트릭 문항을 **만점 처리**하므로 QE가 더해줄 게 없고, 일반 질문에서는 확장 키워드가 오히려 검색을 흐립니다.

### 4-5. Query Expansion 결론

| 상황 | 권장 |
|---|:---:|
| **3B 사용 시** | **OFF** (역효과) |
| 1.5B + 사용자가 매뉴얼 용어 모르고 우회 질문 | ON 고려 (+0.022) |
| 1.5B + 매뉴얼 용어 그대로 질문 | 효과 없음 (승패 반반) |

- **비용**: LLM 호출 1회 추가 → 응답 시간 약 8% 증가 (398s → 429s)
- 프롬프트는 few-shot 예시 2개 + 출력 검증(`_sanitize_expansion()`) 적용된 개선판 기준

📁 `query_expansion_ab_results.csv` (+`_detail`), `hard_set_param_results.csv`, `best_combo_results.csv`

## 5. 검색 파라미터 그리드서치

`chunk_size` × `top_k` 9개 조합, 1.5B, 61문항 (`experiments/tune_rag_params.py`).
overlap은 chunk_size의 1/6로 고정.

| 순위 | chunk_size | overlap | top_k | F1 | 소요(초) |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 1 | **400** | 66 | **4** | **0.7180** | 337.9 |
| 2 | 400 | 66 | 6 | 0.7171 | 337.6 |
| 3 | 600 | 100 | 6 | 0.7159 | 343.0 |
| 4 | 600 | 100 | 4 | 0.7156 ← 기존 기본값 | 353.3 |
| 5 | 800 | 133 | 4 | 0.7150 | 335.4 |
| 6 | 800 | 133 | 6 | 0.7136 | 331.1 |
| 7 | 600 | 100 | **2** | 0.7119 | 325.0 |
| 8 | 800 | 133 | **2** | 0.7110 | 321.3 |
| 9 | 400 | 66 | **2** | 0.7109 | 329.9 |

### 축별 분석

**top_k의 영향** (chunk_size 평균)
| top_k | 평균 F1 |
|:---:|:---:|
| 2 | 0.7113 ← 확실히 최하위 |
| 4 | 0.7162 |
| 6 | 0.7155 |

**chunk_size의 영향** (top_k 평균)
| chunk_size | 평균 F1 |
|:---:|:---:|
| 400 | 0.7153 |
| 600 | 0.7145 |
| 800 | 0.7132 |

### 해석
- **전체 편차 0.0071** (0.7109~0.7180) — RAG 적용(+0.10)이나 모델 크기(+0.048)에 비해 **한 자릿수 작음**
- **top_k=2는 chunk_size와 무관하게 하위 3개를 독식** → 검색 문서가 너무 적으면 확실히 손해
- top_k 4 vs 6은 사실상 동률, chunk_size 간 차이도 미미
- 1위(400/66/4)와 기존 기본값(600/100/4) 차이는 **+0.0024로 노이즈 수준**

## 6. 어려운 세트 (어휘 간극) 검증

### 왜 만들었나
기본 61문항은 매뉴얼 원문의 `"기능명(한글명): 설명"` 패턴을 그대로 질문화해서, **질문과 정답 문단의 어휘가 1:1로 겹칩니다.**

```
질문:      "Pocket 기능은 무엇인가요?"
정답 문단: "Pocket (포켓): 3차원 형상에서 2차원 형상의 공간을 만들어내는 기능이다."
```

이러면 임베딩 검색이 거의 문자열 매칭 수준으로 쉬워져서, 파라미터를 바꿔도 검색 결과가 잘 안 바뀝니다.

### 어떻게 만들었나
**정답 기능명을 질문에서 완전히 배제하고 동작/목적으로만 우회 서술**한 18문항 (`src/hard_benchmark.py`).
자동 검증으로 **기능명 노출 0건** 확인.

| 원본 질문 | 어려운 버전 |
|---|---|
| "Pocket 기능은 무엇인가요?" | "3차원 덩어리에서 안쪽으로 파내어 빈 공간을 만들고 싶습니다. 어떤 기능인가요?" |
| "Chamfer 기능은 언제 사용하나요?" | "날카로운 모서리를 비스듬하게 깎아내고 싶은데 어떻게 하나요?" |
| "Shaft 기능은 무엇인가요?" | "단면을 축 중심으로 빙 돌려서 입체를 만드는 방식은?" |

### 결과 (1.5B)

| 설정 | top_k | QE | F1 | 소요(초) |
|---|:---:|:---:|:---:|:---:|
| top_k=2, QE off | 2 | ✗ | 0.6798 | 73.5 |
| top_k=4, QE off | 4 | ✗ | 0.6788 | 72.8 |
| top_k=6, QE off | 6 | ✗ | 0.6863 | 84.0 |
| **top_k=4, QE on** | 4 | ✓ | **0.7010** | 102.9 |

### 해석
- **어려운 세트 F1(0.68)이 기본 세트(0.72)보다 낮음** → 의도대로 **검색 난이도가 실제로 올라감** 확인
- **설정별 top-1 검색 문서가 18/18 문항 전부 달라짐** → 파라미터가 검색에 제대로 반영된다는 직접 증거
- **여기서는 top_k=6이 top_k=4보다 우세** (0.6863 vs 0.6788) → 질문이 어려울수록 검색을 더 많이 가져오는 게 유리
- **Query Expansion 효과가 기본 세트의 2배 이상** (+0.022 vs +0.010)

📁 `hard_set_param_results.csv` (+`_detail`)

## 7. 최적값 결합 조합 검증

**"각 축의 최적값을 다 합치면 더 좋아질까?"** 를 실제로 측정했습니다.
지금까지 실험은 축을 하나씩만 바꿨기 때문에, 결합 조합은 측정된 적이 없었습니다.

조건: **3B + chunk_size 400/overlap 66 + top_k 4**, 같은 실행에서 QE on/off 동시 측정 (`experiments/test_best_combo.py`)

| 설정 | F1 | 기존 최고 대비 |
|---|:---:|:---:|
| 3B / 600·100 / top_k=4 / QE off (기존 최고) | 0.7648 | — |
| **3B / 400·66 / top_k=4 / QE off** | **0.7654** | **+0.0006** |
| 3B / 400·66 / top_k=4 / QE on | 0.7611 | -0.0037 |

### 유형별
| 질문 유형 | RAG Off | RAG On (QE off) | RAG On (QE on) |
|---|:---:|:---:|:---:|
| General QA | 0.6689 | 0.7367 | 0.7349 |
| Specific QA | 0.6675 | 0.7259 | 0.7191 |
| Trick/Unanswerable | 0.6415 | **1.0000** | **1.0000** |

### 해석
- **+0.0006은 완전한 노이즈** → 1.5B 그리드 1위였던 `400/66`이 **3B에서는 재현되지 않음**

- **"최적값 결합 = 최고 성능"이라는 가정을 실측으로 반증**

## 9. 최종 결론

### 9-1. 성능을 실제로 올린 것

| 레버 | 효과 | 비고 |
|---|:---:|---|
| **RAG 적용** | **+0.100** (3B) | 압도적 1위. 특히 할루시네이션 제거 |
| **모델 크기 1.5B→3B** | **+0.048** | 파라미터 튜닝의 20배 |

### 9-2. 기대만큼 안 통한 것

| 레버 | 결과 | 이유 |
|---|:---:|---|
| Query Expansion | 조건부 (+0.022 ~ -0.004) | 모델이 커지면 불필요, 질문이 쉬우면 무의미 |
| chunk_size / overlap | 노이즈 (+0.0006) | 모델 종속적, 전이 안 됨 |
| top_k | top_k≥4면 무차별 | 단 **top_k=2는 확실히 불리** |

### 9-3. 최종 권장 설정

```yaml
모델:                Qwen/Qwen2.5-3B-Instruct (local GPU)
RAG:                 Strict RAG ON          # 필수
chunk_size/overlap:  600 / 100              # 400/66과 차이 없음
top_k:               4                      # 어려운 질문 위주면 6
Query Expansion:     OFF                    # 3B 기준
```
> **현재 `src/config.py`가 이미 이 조합 — 변경 불필요**

### 9-4. 발표용 스토리

1. **소형 LLM은 CATIA 전문지식이 없어 RAG 없이는 헛소리하거나 답하지 못함** — 트릭 질문 F1 0.61~0.64가 근거
2. **RAG를 붙이면 격차가 크게 벌어지고**(1.5B +0.057 → 3B +0.100), **3B에서는 할루시네이션이 완전히 사라짐**(트릭 문항 만점 1.0000)
3. **성능 기여도는 `RAG 적용 > 모델 크기 >> Query Expansion ≈ 검색 파라미터`** — 앞의 둘만 실제 효과가 있음
4. **엄밀한 검증 과정 자체가 성과**
   - 평가셋을 5 → 61문항으로 확장해 노이즈 제거
   - "최적값을 합치면 더 좋아질 것"이라는 가정을 **실측으로 반증**
   - 어휘 간극 평가셋을 별도 설계해 **검색 난이도 자체를 통제**
   - 실험 중 **벡터스토어 손상을 발견·수리하고 전면 재측정**

### 9-5. 한계 및 향후 과제

- **BERTScore F1의 한계**: 표면적 유사도만 측정하므로, 할루시네이션이어도 표현이 그럴듯하면 점수가 나올 수 있음 → RAGAS `faithfulness` 도입 필요 (OpenAI API 키 이슈로 미완)
- **7B/8B 미검증**: 8GB VRAM 제약으로 양자화 없이는 테스트 불가
- **어려운 세트 18문항은 표본이 작음** → 확대 시 결론이 더 견고해짐
- **Reranking 미시도**: 검색 결과 재정렬은 검증된 기법이나 이번 범위에서 제외

## 부록 B: GPU VRAM 주의사항

**8GB 환경에서 3B 모델 + BERTScore를 동시에 GPU에 올리면 PC가 다운됩니다.**

| 항목 | VRAM |
|---|---:|

| Qwen2.5-3B (fp16) | ~6.2 GB |
| + BERTScore용 BERT 모델 & 활성화 | ~1.5 GB+ |
| **합계** | **8GB 초과 → 드라이버 다운** |

실제로 61문항 생성을 다 끝내고 **저장 직전에 죽어 결과를 통째로 날린 사고**가 있었습니다.

### 해결책 3가지 (`experiments/test_bigger_model.py`에 적용)
1. **채점 전 `free_gpu()` 호출** — LLM 참조를 끊고 `torch.cuda.empty_cache()` (근본 해결)
2. **문항별 중간 저장**(`*_raw.csv`) — 죽어도 생성 결과 보존
3. **BERTScore `batch_size` 64 → 8** — 채점 단계 순간 메모리 완화
